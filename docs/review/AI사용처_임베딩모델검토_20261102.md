## 한눈에

- AI는 **문장을 읽고 쓰는 8곳과 임베딩 1곳**에서만 씁니다. 숫자, 판정, 후보 고르기, 단계 분기는 모두 코드가 합니다. 그래서 AI를 꺼도 판정 건수와 숫자는 같습니다(CR-01).
- 작업마다 더 싼 모델(Flash-Lite), 분류 전용 모델(Jev), 사내 임베딩(BGE-M3)을 후보로 검토했고, 3곳은 실제로 쟀습니다.
- **결론: 모든 곳에서 지금 설정(`gemini-3.8-flash`, `gemini-embedding-001`)을 유지합니다.**
    - 유형 붙이기는 Lite로 내리면 100줄 중 6~10줄을 더 틀렸습니다.
    - 요구사항 추출은 모델을 바꿔도 결과가 같았습니다(코드 규칙이 결정).
    - 임베딩은 Gemini가 정확도·속도 모두 앞섰습니다.
    - 그래서 작업별 모델 설정 기능을 새로 만들 필요가 없고, 기능 동결 전에 코드를 바꾸지 않아도 됩니다.

## 1. AI를 쓰는 곳과 쓰지 않는 곳

### AI를 쓰는 곳

모두 문장을 읽거나 쓰는 일이고, 결과는 코드가 검사합니다.

| # | 작업 | 하는 일 | 코드 위치 | AI 키가 없거나 `off`일 때 |
|---|---|---|---|---|
| 1 | 문서 분류 | 파일명·첫 장으로 문서 종류 판단 보조 | `pipeline/document.py` → `tasks.classify_document` | 규칙 분류만 |
| 2 | 요구사항 추출 | 코드가 고른 문장 후보를 요구사항/작성 규칙/설명으로 구분 (빼기만 함) | `tasks.label_sections` | 건너뜀 |
| 3 | 유형 붙이기 | 규칙표로 못 붙인 줄만 유형 7종 판단 | `tasks.type_unclassified` | 규칙 결과만 |
| 4 | 협조 요청 질문 | 부서별 확인 질문 한 문장 | `pipeline/handoff_mail.py` → `tasks.department_questions` | 부서 기본 문장 |
| 5 | 일탈·질의·제안 문장 초안 | 목록·제안 문장 초안 (숫자는 코드가 채움) | `pipeline/outputs.py`, `proposals.py` → `tasks.draft_sentences` | 코드 기본 문장 |
| 6 | 위험 설명 | 코드가 고른 후보에 "왜 위험한지" 설명 | `pipeline/run.py` → `tasks.explain_risk` | 설명 없이 후보만 |
| 7 | 검증 에이전트 | 위험 설명이 원문으로 뒷받침되는지 다시 확인 | `tasks.check_support` | 건너뜀 |
| 8 | 검토 도우미 | 질문을 받아 읽기 도구를 고르고 답 쓰기 | `pipeline/assistant.py` → `tasks.assistant_step` | 쓸 수 없음 |
| 9 | 임베딩 (뜻 찾기) | 사전 추가 후보, 항목 연결 후보, 지난 확정 힌트 | `pipeline/meaning.py` → `embed_with_retry` | 건너뜀 |

### AI를 쓰지 않는 곳 (코드)

| 묶음 | 단계 |
|---|---|
| 문서 | 구조 나누기(장·절·표·행, 끊긴 표 잇기), **요구사항 후보 고르기**(데이터시트 표 줄, 공급사 C/D/E 표시 줄, shall·must 등이 든 문장), 문서 종류별 처리기 선택과 처리 뒤 점검 |
| 값·판정 | 값 정리(숫자·단위·비교 기호), 위험 후보 고르기(위험 표현 사전·값 비교), 공학 규칙 검산, 적합성 판정 5종과 여유 계산, 보증값 후보, 손실 환산 |
| 후보·전달 | 기술 제안 포인트 후보 고르기, 문서 읽기 점검, 유형별 담당 부서 배정, 메일 보내기 |
| 흐름·관리 | 승인 기준(AR) 판단, 단계 순서와 분기(LangGraph `NEXT` 표), 정답지 채점 |

**요구사항 추출에서 코드와 AI의 나눔**: 코드가 규칙으로 후보를 올리고, AI는 문장 후보 중 요구사항이 아닌 것을 **빼기만** 합니다. 그래서 놓친 줄(K1)은 코드 규칙이 상한을 정하고, 어떤 모델을 써도 규칙이 못 올린 줄은 찾지 못합니다.

### 처음 추천에서 바뀐 점

| 처음 생각 | 측정 후 |

| 분류형 작업(1~4번)은 Lite로 내리면 된다 | 유형 붙이기(3번)는 Lite로 내리면 정확도가 떨어졌다. 요구사항 추출(2번)은 모델과 무관했다 |

### 측정하지 않은 곳과 이유

9곳 중 6곳(1번 일부, 4~8번)은 이번에 재지 않았습니다. 공통 이유는 세 가지입니다.

1. **바꾸지 않기로 한 곳이라 증명 부담이 작습니다.** 측정은 "더 싼 모델로 바꿔도 되는가"를 보일 때 필요합니다. 이 작업들은 처음부터 3.8 Flash 유지를 추천했고, 측정한 유형 붙이기에서도 Lite가 정확도를 잃었습니다.
2. **정답이 없는 작업입니다.** 유형 붙이기·요구사항 추출은 맞다/틀리다를 가릴 정답지가 있었지만, 설명·초안·답변은 "얼마나 좋은 문장인가"라서 사람이 읽어 봐야 합니다.
3. **이번에 쓴 문서로는 결과가 나오지 않습니다.** 파일 18은 묶음 C(추출만)라 판정이 없고, 그래서 일탈·질의 초안, 제안 포인트, 협조 요청 질문이 만들어지지 않습니다.

## 6. 발표에서 쓸 문장

> "AI는 문장을 읽고 쓰는 일만 하고, 숫자와 판정은 코드가 합니다. AI를 쓰는 곳마다 더 싼 모델과 분류 전용 모델을 같은 정답지로 비교했습니다. Lite는 2~5초 빠르고 35~60 % 싸지만 6~10줄을 더 틀려서 3.8 Flash를 유지했습니다. Jev는 프롬프트 개선 전에는 9줄을 보태 줬지만 개선 후에는 1줄이라 쓰지 않았습니다. 임베딩은 Gemini가 BGE-M3보다 영어↔한국어 정확도가 20%p 높아 유지하고, BGE-M3는 외부 전송이 막힐 때의 대안으로 둡니다."

측정하지 않은 곳(협조 요청 질문, 문장 초안, 위험 설명, 검증 에이전트, 검토 도우미, 문서 분류의 Lite 쪽)은 이렇게 설명합니다.

> "정답이 없는 문장 작업이고 호출이 적어, 비용을 줄이는 이득보다 품질 위험이 커서 3.8 Flash로 두었습니다. 다음 단계로 코드 검사 통과율(근거 대조로 버려진 비율, 기본 문장으로 바뀐 비율)로 비교할 계획입니다."
