## 한눈에

- AI는 **문장을 읽고 쓰는 8곳과 임베딩 1곳**에서만 씁니다. 숫자, 판정, 후보 고르기, 단계 분기는 모두 코드가 합니다. 그래서 AI를 꺼도 판정 건수와 숫자는 같습니다(CR-01). 이번 측정에서도 모델을 바꿔도 판정 5종 건수가 완전히 같았습니다.
- 더 싼 모델(Flash-Lite), 분류 전용 모델(Jev), 사내 임베딩(BGE-M3)을 후보로 검토하고, 실제 RFP 두 건(파일 1·18)과 정답지로 쟀습니다.
- **결론: 모든 곳에서 지금 설정(`gemini-3.8-flash`, `gemini-embedding-001`)을 유지합니다.**
    - 3.5 Flash-Lite는 처리 시간 −56 %, 비용 −47 %이지만, AI가 실제로 판단하는 부분에서 3.8 Flash보다 못했습니다. 두 모델 판단이 갈린 요구사항 문장 17줄 중 3.8이 13줄, Lite가 3줄을 맞혔고, 문장 초안은 Lite만 9개 중 4개가 검사에 걸렸습니다.
    - 아끼는 돈은 파일 1 한 건에 약 300원입니다.
    - 임베딩은 Gemini가 정확도·속도 모두 앞섰습니다.
- **측정 중 버그를 하나 찾았습니다.** Docker로 실행하면 `.env`의 `GEMINI_MODEL`·`RFP_AI_MODE`가 백엔드에 전달되지 않습니다(8장).

## 1. AI를 쓰는 곳과 쓰지 않는 곳

### AI를 쓰는 곳

모두 문장을 읽거나 쓰는 일이고, 결과는 코드가 검사합니다.

| # | 작업 | 하는 일 | 코드 위치 | AI 키가 없거나 `off`일 때 |
|---|---|---|---|---|
| 1 | 문서 분류 | 파일명·첫 장으로 문서 종류 판단 보조 | `pipeline/document.py` → `tasks.classify_document` | 규칙 분류만 |
| 2 | 요구사항 추출 | 코드가 고른 문장 후보를 요구사항/작성 규칙/설명으로 구분 (빼기만 함) | `tasks.label_sections` | 건너뜀 |
| 3 | 유형 붙이기 | 규칙표로 못 붙인 줄만 유형 7종 판단 | `tasks.type_unclassified` | 규칙 결과만 |
| 4 | 협조 요청 질문 | 부서별 확인 질문 한 문장 | `pipeline/handoff_mail.py` → `tasks.department_questions` | 부서 기본 문장 |
| 5 | 일탈·질의·제안 문장 초안 | 목록·제안 문장 초안 (숫자는 코드가 채움) | `pipeline/outputs.py`, `proposals.py` → `tasks.draft_sentences` | 코드 기본 문장 |

| 9 | 임베딩 (뜻 찾기) | 사전 추가 후보, 항목 연결 후보, 지난 확정 힌트 | `pipeline/meaning.py` → `embed_with_retry` | 건너뜀 |

### AI를 쓰지 않는 곳 (코드)

| 묶음 | 단계 |
|---|---|
| 문서 | 구조 나누기(장·절·표·행, 끊긴 표 잇기), **요구사항 후보 고르기**(데이터시트 표 줄, 공급사 C/D/E 표시 줄, shall·must 등이 든 문장), 문서 종류별 처리기 선택과 처리 뒤 점검 |
| 값·판정 | 값 정리(숫자·단위·비교 기호), 위험 후보 고르기(위험 표현 사전·값 비교), 공학 규칙 검산, 적합성 판정 5종과 여유 계산, 보증값 후보, 손실 환산 |
| 후보·전달 | 기술 제안 포인트 후보 고르기, 문서 읽기 점검, 유형별 담당 부서 배정, 메일 보내기 |
| 흐름·관리 | 승인 기준(AR) 판단, 단계 순서와 분기(LangGraph `NEXT` 표), 정답지 채점 |

**요구사항 추출에서 코드와 AI의 나눔**: 코드가 규칙으로 후보를 올리고, AI는 문장 후보 중 요구사항이 아닌 것을 **빼기만** 합니다. 파일 1은 요구사항 4,895줄 중 4,875줄(99.6 %), 파일 18은 153줄 중 120줄이 코드가 바로 뽑은 표 줄이고, AI가 판단하는 것은 나머지 문장뿐입니다. 그래서 놓친 줄(K1)은 코드 규칙이 상한을 정하고, AI는 남은 문장의 정확도(K2)에 영향을 줍니다.

### 3-3. 요구사항 놓친 줄 진단 (파일 18, K1 66.5 %)

`experiments/diag/diag_missed.py`로 정답 200줄을 상태별로 나눔.

| 상태 | 공급사 표시 있음 | 표시 없음 |
|---|---|---|
| 찾음 | 102 | 31 |
| 추출 안 됨 | 0 | 67 |

- 공급사가 C/D/E를 단 줄은 모두 찾았습니다. 놓친 67줄은 전부 표시가 없는 줄이고, 코드가 후보로 올리지 않아 AI까지 가지 않았습니다. **모델과 무관한 코드 규칙 문제입니다.**
- 놓친 줄 모양(어림): 명령문 "Provide …", "Install …" 약 31줄, 표 안의 "항목: 값" 사양 줄 약 10줄, 하위 목록 항목 약 10줄, 허용 제조사 목록 약 7줄, 제목 약 5줄.

## 6. 발표에서 쓸 문장

> "AI는 문장을 읽고 쓰는 일만 하고, 숫자와 판정은 코드가 합니다. 모델을 바꿔도 판정 건수가 하나도 달라지지 않는 것으로 확인했습니다. AI를 쓰는 곳마다 더 싼 모델을 실제 RFP로 비교했습니다. 3.5 Flash-Lite는 처리 시간을 6.3분에서 2.8분으로, 비용을 634원에서 335원으로 줄였지만, 두 모델 판단이 갈린 요구사항 문장 17줄 중 3.8 Flash가 13줄을 맞혔고, Lite는 서식 작성 안내를 요구사항으로 남겼습니다. 그래서 품질을 위해 3.8 Flash를 유지했습니다. 임베딩은 Gemini가 BGE-M3보다 영어↔한국어 정확도가 20%p 높아 유지하고, BGE-M3는 외부 전송이 막힐 때의 대안으로 둡니다."

측정하지 못한 곳(협조 요청 질문, 위험 설명, 검증 에이전트, 검토 도우미)은 이렇게 설명합니다.

> "이번에 쓴 두 문서에는 위험 후보와 협조 요청 메일이 없어 결과가 나오지 않았습니다. 측정한 다른 작업에서 Lite가 이미 품질을 잃었으므로 3.8 Flash로 두었고, 위험 후보가 있는 문서로 추가 측정할 계획입니다."

## 8. 발견한 버그: Docker에서 모델·AI 방식 설정이 전달되지 않음

- **증상**: `.env`의 `GEMINI_MODEL`을 바꾸고 백엔드를 다시 켜도 모델이 바뀌지 않습니다. 이 때문에 첫 비교(run 32, run 34)는 Lite가 아니라 3.8 Flash로 돌았고, 그 결과를 "결과가 같다"로 잘못 해석했다가 바로잡았습니다.
- **원인**: `docker-compose.yml`의 `backend.environment`가 `.env`에서 일부 값만 넘깁니다(`GEMINI_API_KEY`, `RFP_LLM_WORKERS`, 메일 설정 등). `GEMINI_MODEL`, `RFP_AI_MODE`, `RFP_LOCAL_LLM_*`, `RFP_DOC_WORKERS`는 목록에 없어 늘 기본값을 씁니다. `.env` 파일 자체는 컨테이너에 붙지 않습니다.
- **영향**: Docker로 실행하면 기획서 5-6·명세서 NFR-07의 "AI 사용 방식 설정"(Gemini·사내 모델·AI 끄기)이 동작하지 않습니다. 데이터 보안 설명에서 이 설정을 근거로 들 때 질문받을 수 있습니다.
- **이번 측정에서 한 임시 조치**: 저장소 맨 위에 `docker-compose.override.yml`을 만들어 `GEMINI_MODEL`만 넘겼습니다. 측정 뒤 지웁니다.
- **고치는 방법 (제안)**: `docker-compose.yml`의 `backend.environment`에 아래 줄을 더하고 PR로 올립니다.

  ```yaml
  GEMINI_MODEL: ${GEMINI_MODEL:-gemini-3.8-flash}
  RFP_AI_MODE: ${RFP_AI_MODE:-gemini}
  RFP_LOCAL_LLM_URL: ${RFP_LOCAL_LLM_URL:-}
  RFP_LOCAL_LLM_MODEL: ${RFP_LOCAL_LLM_MODEL:-}
  RFP_LOCAL_LLM_KEY: ${RFP_LOCAL_LLM_KEY:-}
  RFP_LOCAL_EMBED_MODEL: ${RFP_LOCAL_EMBED_MODEL:-}
  RFP_DOC_WORKERS: ${RFP_DOC_WORKERS:-2}
  ```

  `.env.example`에도 `RFP_AI_MODE`와 사내 모델 설정 줄이 없으니 함께 더합니다.

참고로 같은 측정 중에 마이그레이션 번호가 바뀐 파일(예전 `0014_document_content_hash`·`0014_claim_evidence` → 지금 `0015`·`0016`) 때문에 백엔드가 켜지지 않는 문제도 있었습니다. 10-29 이전에 DB를 만든 팀원은 같은 오류가 날 수 있습니다. 내용이 같은 파일이라 `schema_migration` 표에 새 이름을 "적용함"으로 기록하면 해결됩니다.
