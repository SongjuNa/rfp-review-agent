# 강사님 피드백(10-29) 반영 · RFP 검토 시스템 개선 방향

작성일: 2026-10-29 · 기준 커밋: main `23d6322` (PR #18 머지 뒤) · 출처: 10-29 강사님 피드백 녹음 정리본(노션 내보내기)

> 이 문서는 제안입니다. 아래 change는 아직 만들지 않았고, 팀이 정한 뒤 AGENTS.md 순서대로 OpenSpec change부터 만듭니다.

## 한눈에

강사님 피드백 15개 중 RFP 검토 시스템에 해당하는 것은 9개이고, 그중 가장 크게 비어 있는 곳은 **"사람이 검증한 결과와 비교해 정확도를 보여 주기"(3-15)**입니다. 정답지·채점 화면(SCR-19)이 지금 예시 데이터뿐이라, 기능 동결(11-04) 전에 이것부터 채우기를 추천합니다.

피드백 중 상담 업무(접수함·상담원 챗봇·전화 상담) 이야기는 다른 주제라 뺐습니다.

추천 순서 (기능 동결까지 영업일 약 4일)

1. **정답지·채점기와 개선 기록** (3-15, 3-8): 사람이 확정한 판정과 시스템 판정을 비교해 일치율을 보여 주고, 고칠 때마다 "전 → 후" 점수를 남긴다. 약 2일.
2. **검토 상세 맨 위 "먼저 볼 것" 요약과 "AI가 한 일" 띠** (3-4, 3-9, 3-8, 3-12): 일탈·질의·위험 조건 중 큰 것부터 3~5줄, 사람이 꼭 볼 것과 묶어서 확정해도 되는 것을 나눠 보여 주고, 처리 시간도 같이 적는다. 약 1일.
3. **협조 요청을 메일 초안으로 내보내고 자동으로 "보냄" 기록** (3-14): 받는 부서가 이 시스템을 안 봐도 되게 하고, 보낸 사실을 따로 체크하지 않게 한다. 약 1일.
4. 메일 수신 연동, 사내 메신저 알림, 관리자 대시보드 실데이터, 벡터 검색은 만들지 않고 발표에서 **한계와 다음 단계**로 말한다.

## 개선 제안

세 가지 모두 새 기능이라 AGENTS.md 순서대로 OpenSpec change를 먼저 만들고 팀 확인 후 구현합니다. 모든 결과는 계속 "후보"이고 확정은 사람(CR-08)이라는 원칙은 바꾸지 않습니다.

### 1. 정답지·채점기와 개선 기록 (change 예: `add-evaluation`)

- **왜**: 강사님이 "새 AI를 만들 때 가장 먼저 하는 일"이라고 한 부분(3-15)이고, 최종평가 "AI 기술 활용성 35점"의 "테스트를 통한 개선 과정"과 그대로 겹칩니다. 10-27 현업 멘토의 "사람이 고친 결과를 쌓아라"는 요구와도 같은 방향입니다.
- **무엇을**: (1) 사람이 확정한 판정(FR-10 이력)과 유형 정답지 CSV를 정답으로 삼고, (2) 시스템 결과와 비교해 SCR-19의 지표(요구사항 찾기 재현율·원문 위치 정확도·판정 일치율 등)를 코드로 계산하고, (3) 규칙·사전을 고칠 때마다 "날짜 · 고친 곳 · 점수 전 → 후"를 한 줄씩 남깁니다. SCR-19 화면은 이미 이 모양이라 예시 데이터를 실제 값으로 바꾸면 됩니다.
- **얼마나**: 약 2일. 11-05 K1~K12 측정 전에 필요합니다.
- **발표 그림**: "처음 판정 일치율 ○% → 비교 방향 사전을 고친 뒤 ○% → …" 같은 트러블슈팅 표. 숫자는 실제 측정값만 씁니다.

### 2. 검토 상세 맨 위 "먼저 볼 것"과 "AI가 한 일" (change 예: `update-review-summary`)

- **왜**: "의심되는 부분을 먼저, 결재권자는 가장 중요한 것만"(3-9), "AI가 업무를 어떻게 돕는지 안 보인다"(3-4), "중요도별로 검증 깊이를 다르게"(3-8), "느리면 안 쓴다"(3-12)를 한 자리에서 답합니다.
- **무엇을**: 검토 상세와 결재 대기 화면 맨 위에 세 줄을 둔다.
    - **AI가 한 일**: "문서 ○개에서 요구사항 ○개를 찾아 제품표와 비교했습니다. 걸린 시간 ○분". 건수는 `judgment-counts`, 시간은 `started_at`~`finished_at`으로 코드가 채웁니다(CR-01).
    - **먼저 볼 것 3~5줄**: 일탈 후보 → 위험 조건 → 질의 후보 순서, 같은 종류 안에서는 팀 가정·낮은 신뢰도인 줄을 위로. 줄마다 원문 위치 링크.
    - **확인 깊이 3단**: "사람이 꼭 볼 것 ○줄(일탈·질의·위험) / 묶어서 확정해도 되는 것 ○줄(준수) / 숫자·판정을 코드가 한 것 ○줄". 지금 있는 멈춤 지점·한꺼번에 확정 규칙을 이름만 붙여 보여 주는 것이라 새 판정 규칙은 없습니다.
- **얼마나**: 약 1일. 새 API는 요약 하나(기존 쿼리 재사용)이고 `npm run gen:api`로 타입을 다시 만듭니다.
- **더 하면 좋은 것**: 단계별 걸린 시간을 `graph_state`에 남겨 처리 상태 화면에 보여 주기(반나절). AS-IS는 현업 멘토링에서 들은 "기술 검토 보통 7~10일".

### 3. 협조 요청을 메일 초안으로 (change 예: `add-request-mail`)

- **왜**: "받는 부서가 이 시스템을 볼 확률은 거의 없다. 요청했다고 따로 체크하면 이중 업무"(3-14).
- **무엇을**: 협조 요청 화면(SCR-13)에서 담당 부서를 고르면, 그 부서에 간 할 일(항목·요구값·원문 위치·물어볼 점)을 메일 본문 초안과 첨부 엑셀로 만듭니다. 사용자가 자기 메일 프로그램에서 보내고, 초안을 만든 순간 시스템이 "메일 초안 만듦, 시각"을 자동 기록해 따로 체크할 일이 없게 합니다. 본문 문장은 정해진 틀에 코드가 값을 채웁니다(언어 모델 안 씀).
- **얼마나**: 약 1일. 직접 보내기(메일 서버)와 회신 자동 읽기는 하지 않습니다. 외부로 나가는 동작이고 메일 서버 인증이 필요하기 때문입니다.

### 시간이 남으면: 지난 수정 힌트 (3-5)

같은 항목·같은 요구값을 사람이 예전에 고친 적이 있으면 판정 줄에 "지난번 검토에서 ○○으로 고침"을 보여 줍니다. 판정을 자동으로 바꾸지는 않고 힌트만 내므로 CR-08·CR-11을 지킵니다. 찾기는 글자 일치로 충분해 벡터 검색은 필요 없습니다 [제안]. 약 1일.

| 말할 것 | 한 문장 예시 | 관련 피드백 |
| --- | --- | --- |
| 근거 보기 | "모든 값은 누르면 RFP 원문의 절·표·행으로 갑니다. 위치가 없는 값은 아예 화면에 나오지 않습니다." | 3-10 |
| 역할 나눔 | "언어 모델은 문장 읽기·초안만, 숫자·판정은 코드, 확정은 사람입니다." (등록 → 판정 → 확인 → 결재 흐름 그림에 색으로 표시) | 3-8 |
| 문서 형식 통일 | "고객사마다 다른 수백 쪽 RFP를 같은 판정표·TBE 준수표·데이터시트 형식으로 정리합니다." | 3-13 |

| 한계: 메일 수신·사내 메신저 | "지금은 메일 초안을 만들고 보낸 기록을 남깁니다. 회신 자동 읽기와 사내 메신저 알림은 사내 메일 서버 권한이 필요해 다음 단계입니다." | 3-7, 3-14 |
| 한계: 관리자 대시보드 | "팀 현황 화면은 목업 단계입니다. 목적은 '팀장이 막힌 단계와 기한 넘긴 검토를 찾는 화면'으로 정했습니다." | 3-1, 3-2 |
| 한계: 과거 사례 검색 | "지난 RFP 비교·입찰 이력은 화면만 있고, 실제 연결은 입찰 결과 데이터를 받은 뒤 합니다." | 3-5 |
