# RFP 검토 시스템 테스트 방법과 검토자 확인 사항

작성일: 2026-10-29 · 기준 커밋: main `23d6322` (PR #18 머지 뒤)

11-03 갱신: 테스트 숫자와 화면 상태를 지금에 맞췄습니다(기준: main `e544fa5`의 GitHub CI). 실제로 돌린 결과는 "테스트 결과를 남기는 방법"의 기록표에 있습니다.

## 요약

이 문서는 RFP 검토 시스템(화면 이름 Spec2Win)이 제대로 돌아가는지 확인하는 방법을, 처음 보는 팀원도 그대로 따라 할 수 있도록 적은 것입니다.

테스트는 세 단계로 나눕니다. 단계마다 확인할 수 있는 것이 다르기 때문입니다.

1. **1단계, 자동 테스트**: 명령 몇 줄로 코드가 깨지지 않았는지 확인합니다. 11-03 main 기준 백엔드 테스트 559개가 통과하고 30개는 건너뜁니다(GitHub CI). 화면 자동 테스트 파일은 55개입니다. 다만 화면 자동 테스트는 실제 RFP가 아니라 테스트용으로 만든 합성 문서로 돕니다.
2. **2단계, 실제 RFP 한 건을 처음부터 끝까지 돌리기**: 원본 파일 "1. Bidding Forms_Draft"를 올려서 등록 → 분석 → 판정 확인 → 내려받기 → 협조 요청 → 결재 상신 → 승인까지 사람이 직접 눌러 봅니다. 11-03에 처음 끝까지 돌렸습니다(RV-2026-037, 결과는 기록표). 이 흐름을 자동으로 도는 화면 테스트(`frontend/e2e/review.spec.ts`)는 RFP 원문이 서버 폴더에 없으면 건너뛰므로, GitHub CI에서는 늘 건너뜁니다.
3. **3단계, 파일별·규칙별 확인**: 특정 원본 파일에서만 확인할 수 있는 것(위험 표현, 한국어 문서, 이미지만 있던 문서 등)과, 공통 규칙(CR-01~12)을 시스템이 지키는지 점검합니다.

문서 끝의 "검토자가 확인해야 하는 산출물 항목"에는 개발하면서 팀 확인을 받지 못한 채 남은 결정, 비어 있는 데이터, 오래되어 고쳐야 할 안내 문서를 모았습니다. 테스트와 별도로 사람이 판단해야 하는 것들입니다.

## 준비

설치는 [`docs/setup-guide.md`](../setup-guide.md)(내 컴퓨터에서 설치하고 실행하기) 1장, 2장을 그대로 따라 하면 됩니다. 그 문서의 3장 "써 보기"는 짧은 둘러보기이고, 테스트할 때는 이 문서의 2단계를 따르세요.

### 준비 순서

1. 저장소를 최신으로 받습니다. `git pull` 뒤 Docker라면 `docker compose up --build`, 직접 실행이라면 `uv sync`와 `npm install`을 다시 합니다.
2. DB를 최신 구조로 맞추고 사전과 제품표를 넣습니다. 직접 실행이라면 `cd backend && uv run rfp-db setup`, Docker라면 `docker compose exec backend rfp-db setup`입니다. 10-29 머지로 마이그레이션 0009~0011(검토 정보, 결재 흐름, 문서 읽기 점검)이 추가되었으므로, 예전에 설치한 사람도 한 번은 꼭 돌려야 합니다. 제품표가 제대로 들어가면 제품 122개(중전압 기기 97, 서지 보호기 20, GIS 4, 변압기 1)가 보여야 합니다.
3. 언어 모델 키를 저장소 맨 위 `.env` 파일의 `GEMINI_API_KEY=` 뒤에 넣습니다. 키가 없어도 시스템은 돌지만, 언어 모델이 하는 단계(문장 읽기 보조, 일탈·질의 문장 초안, 제안 포인트 문장)는 건너뛰거나 비어 있게 됩니다. 키가 있을 때와 없을 때를 모두 테스트해 보는 것을 추천합니다. 참고로 "1. Bidding Forms_Draft" 한 건을 키를 넣고 돌리는 데 드는 비용은 이전 실측으로 약 680원이었습니다.
4. 팀 공유 폴더의 `RFP_Cleansed_styled_v6.zip`을 풀어서, 안에 있는 docx 22개를 저장소의 `data/private/rfp_docx/` 폴더에 넣습니다. 이 폴더에 파일이 있어야 등록 화면에 "서버에 둔 RFP에서 고르기"가 보이고, 자동 테스트 `review.spec.ts`도 건너뛰지 않고 실제로 돕니다. 이 폴더는 git이 무시하도록 되어 있으므로 GitHub에 올라가지 않습니다.
5. 화면은 크롬에서 http://localhost:5173 을 엽니다. 화면에는 로그인이 없고, 머리글 오른쪽 위의 사용자 칩을 눌러 엔지니어, 승인자(결재자), 견적 담당, 품질 담당, 영업 담당으로 바꿉니다.

## 1단계: 자동 테스트

아래 명령은 AGENTS.md 7장 "완료 기준"과 같으며, GitHub에 올릴 때 자동 검사(CI)도 같은 것을 돌립니다. 모두 저장소 폴더 안에서 실행합니다. 백엔드 테스트는 DB를 지웠다가 다시 만들기 때문에 개발용 DB(`rfp`)가 아닌 테스트용 DB(`rfp_test`)를 씁니다. 처음 한 번만 `docker compose exec db createdb -U rfp rfp_test`로 만들어 둡니다.

| 순서 | 명령 | 무엇을 확인하는가 | 통과로 보는 모양 |
| --- | --- | --- | --- |
| 1 | `cd backend && uv run ruff check .` | Python 코드의 문법·스타일 오류 | "All checks passed!" |
| 2 | `cd backend && TEST_DATABASE_URL=postgresql://rfp:rfp@localhost:5433/rfp_test uv run pytest` | 백엔드 기능 테스트(11-03 main CI: 559개 통과, 30개 건너뜀. 건너뛰는 것은 고객 원문이나 AI 키가 있어야 도는 테스트). 스펙의 Scenario(상황별 요구사항)마다 테스트가 하나 이상 있습니다. 예를 들어 "위치가 없는 근거는 내보내지 않는다", "일탈 후보가 있으면 멈춘다" 같은 규칙을 검사합니다 | 마지막 줄에 "passed"만 있고 "failed"가 없음 |
| 3 | `cd frontend && npm run lint` | 화면 코드의 문법 오류 | 오류 0개 |
| 4 | `cd frontend && npm run check:api` | 백엔드 응답 모양과 화면이 쓰는 타입이 같은지. 다르면 화면이 빈 칸을 보여 줄 수 있습니다 | 차이 없음 |
| 5 | `cd frontend && npm run build` | 화면이 끝까지 만들어지는지(타입 검사 포함) | "built in" 줄이 나옴 |
| 6 | `npx -y @fission-ai/openspec@1.14.3 validate --all --strict` | 스펙 문서의 형식(요구사항마다 Scenario가 있는지 등) | 모두 valid |
| 7 | 백엔드(8000)와 `npm run dev`(5173)를 켜 둔 채 `cd frontend && npm run e2e` | 브라우저를 자동으로 움직여 화면을 누르는 테스트 55개 파일. 결재 흐름, 한꺼번에 확정, TBE·데이터시트 내려받기, 정답지·채점, 예시 화면 띠 등. **GitHub CI에서는 돌지 않습니다** | "failed"가 없음. 전체를 마지막으로 돌린 기록은 10-29(파일 25개 때 "65개 통과, 1개 건너뜀")이고, 11-03에는 핵심 흐름(`core-flow.spec.ts`)만 통과 확인 |

주의할 점이 두 가지 있습니다.

- e2e 테스트는 실제 RFP가 아니라 테스트용 합성 문서로 돕니다. 그래서 "단추가 눌리고 값이 저장되는가"는 확인하지만, "실제 RFP에서 판정이 맞는가"는 확인하지 못합니다. 그 부분은 2단계에서 사람이 봅니다.
- 실제 RFP로 도는 e2e(`review.spec.ts`, "파일 1을 올려 확인·승인까지")는 `data/private/rfp_docx/`에 "00지역_문서검토_1. Bidding Forms_Draft_교육용클렌징v6.docx"가 있어야 돕니다. 파일을 넣고 돌렸을 때 통과하는지가 이번 테스트의 첫 번째 확인거리입니다. 이 테스트는 GitHub CI에서는 원문이 없어서 항상 건너뛰므로, 내 컴퓨터에서만 확인할 수 있습니다.

## 2단계: 실제 RFP 한 건을 처음부터 끝까지

원본 파일 "00지역_문서검토_1. Bidding Forms_Draft_교육용클렌징v6.docx" 한 개로 검토 흐름 순서대로 따라가면, 실제로 동작하는 화면을 한 번에 모두 지나갑니다. 단계마다 "확인할 것"을 보고, 다르면 화면을 캡처해 기록표에 남깁니다. "기대 결과"는 개발 중에 같은 파일로 확인했던 값이라, 다르게 나오면 시스템이나 기대값 중 하나가 틀린 것이므로 두 가지를 모두 의심해 봅니다.

### 2-1. 검토 등록 (엔지니어로)

1. 머리글 오른쪽 위 사용자 칩에서 엔지니어를 고릅니다.
2. 왼쪽 메뉴 "RFP 관리" → "RFP 등록"을 누릅니다. "서버에 둔 RFP에서 고르기"에서 위 파일을 고르거나, docx를 끌어다 놓습니다.
3. "검토 정보" 단계에서 사업명, 검토명, 고객사, 국가, 마감일, 담당 엔지니어를 넣고 등록합니다. 고객사명은 실제 이름 대신 "테스트 고객사"처럼 적습니다.

확인할 것: 등록하자마자 처리 상태 화면으로 넘어가는지, 마감일을 오늘보다 이전으로 넣으면 막히거나 경고가 나오는지.

### 2-2. 처리 상태 화면

단계별 진행 막대가 문서 분류 → 구조 나누기 → 요구사항 찾기 → 유형 붙이기 → 값 읽기 → 위험 조건 찾기 → 판정 → 결과물 만들기 순서로 넘어가는지 봅니다. 키 없이는 약 30초, 키가 있으면 수 분 걸립니다.

확인할 것: 끝나면 스스로 검토 상세로 넘어가는지, 걸린 시간(시작·끝 시각)을 기록해 둡니다. 이 시간은 기획서 2-3 "측정한 것" 표의 처리 시간이 됩니다. 사람이 손으로 할 때는 "기술 검토 보통 7~10일"(현업 멘토링, LS 영업 담당자)이라는 말이 참고로 있지만, 같은 조건에서 잰 값이 아니라 단축률로 계산하지는 않습니다(11-03).

### 2-3. 검토 상세: 판정 탭 (제품의 핵심)

1. 머리글의 요약 칸 5개(일탈 후보, 질의 후보, 확인 필요, 작성 필요, 준수)의 숫자를 적어 둡니다.
2. 판정 탭에서 일탈 후보 5줄, 질의 후보 3줄, 준수 2줄을 골라 줄을 눌러 오른쪽에 나오는 내용을 봅니다.
3. 각 줄에서 다음 네 가지를 원본 docx를 직접 열어 대조합니다.
    - (가) 원문 위치(파일, 절 또는 표, 행)가 실제로 그 문장을 가리키는가.
    - (나) 요구값과 단위를 원문 그대로 읽었는가.
    - (다) 비교한 제품과 제품값이 제품표와 같은가.
    - (라) 일탈·질의·준수 판정이 엔지니어가 봐도 맞는가.
4. 판정 하나를 골라 사유를 적고 바꿉니다. 사유를 비우면 저장이 막혀야 합니다.
5. 준수 줄 여러 개를 골라 "한꺼번에 확정"을 누릅니다.

기대 결과: 정격 전류 4,000 A 요구가 일탈 후보로 묶여 나오고, 245 kV 차단기의 차단 전류 100 kA가 공학 규칙 검산에서 위반(계산상 125 kA가 맞음)으로 걸려 질의 후보가 됩니다. 두 값은 개발 기록에서 확인한 것이고, 이번에 다시 확인해야 합니다. 원문 위치가 없는 줄은 화면에 나오지 않아야 합니다(CR-02·03).

### 2-5. 내려받기 세 가지

1. 일탈 목록·질의서 초안(검토 상세의 초안 화면): 문장을 하나 확정, 하나 고치기, 하나 빼기를 한 뒤 Word로 내려받아 엽니다. 뺀 문장이 파일에 없는지, 문장 안 숫자가 판정 화면의 숫자와 같은지 봅니다.
2. TBE 준수표: 기준·넣을 줄·언어를 골라 엑셀로 내려받습니다. 줄 수가 화면 미리보기와 같은지, 원문 위치 칸이 채워져 있는지 봅니다.
3. 데이터시트 채우기: 칸 몇 개를 확정하고 "확인 필요만 보기"를 켜 본 뒤 엑셀로 내려받습니다. "1. Bidding Forms_Draft"의 데이터시트 칸이 고객 양식 순서대로 빠짐없이 나오는지, 모르는 값이 빈칸으로 남아 있는지(CR-04) 봅니다.

### 2-6. 협조 요청 (견적·품질·영업 담당으로)

사용자를 견적 담당으로 바꾼 뒤 "협조 요청" 메뉴에서 자기 부서 탭을 열고 항목 하나를 "확인"합니다. 품질 담당, 영업 담당으로도 반복합니다.

확인할 것: 비용과 관련된 요구는 견적 담당에게, 시험·인증은 품질 담당에게 갔는지. 글자가 같은 조건이 한 건으로 묶였는지. 엔지니어 몫인 기술 요구는 다른 부서로 가지 않았는지. 재요청·내보내기가 회색으로 잠긴 것은 아직 만들지 않은 기능이라 정상입니다.

### 2-7. 결재 상신과 승인

1. 엔지니어로 돌아와 검토 상세에서 결재 상신 창을 엽니다. 상신 전 확인 결과를 보고, 결재자를 골라 의견과 함께 상신합니다.
2. 상신한 뒤 "상신 취소"도 한 번 해 보고 다시 상신합니다.
3. 사용자를 고르지 않은 다른 승인자로 바꿔 결재 대기 화면을 열고, 승인·반려 단추가 없는지 봅니다.
4. 지정한 결재자로 바꿔 한 번은 반려(의견 필수), 다시 상신한 뒤 승인합니다.
5. 제출본 탭에 v1이 생기고, 이력 탭에 상신·취소·반려·승인이 모두 남았는지 봅니다.

기대 결과: "1. Bidding Forms_Draft"는 확인 필요 비율이 높아서, 상신 전 확인에 승인 기준 AR-03(확인 필요 20 % 초과)이 걸립니다. 개발 때는 이 파일에서 항상 걸렸습니다.

### 2-8. 홈과 검토 목록

홈과 검토 목록에서 방금 검토의 단계(판정 확인 → 결재 대기 → 제출 준비)가 맞게 바뀌었는지, 사용자를 바꾸면 "내가 처리할 건"이 맞게 바뀌는지 봅니다. 마감일을 3일 안으로 넣은 검토는 "3일 내 마감"에 세어져야 합니다.

### 2-9. 일부러 실패시키기

메모장으로 아무 글자나 적어 저장한 뒤 파일 이름 끝만 .docx로 바꾼 가짜 파일을 등록합니다. 겉모양만 docx이고 속은 docx가 아니라서 분석이 실패해야 합니다. 분석 실패 화면에 멈춘 단계, 오류 문장, 처리 기록이 나오고, 홈에 분석 실패 알림이 뜨는지 봅니다. 작업이 끝나면 테스트용 가짜 파일은 지웁니다.

### 3-2. 공통 규칙을 지키는지 점검

명세서 2장의 공통 규칙은 이 시스템의 신뢰성 근거입니다. 2단계를 하면서 같이 확인하고, 확인한 줄에 표시합니다.

- [ ] CR-01: 숫자, 판정, 후보 고르기는 언어 모델 키가 없어도 같은 결과가 나온다. (키 없이 한 번, 키를 넣고 한 번 돌려 판정 건수를 비교합니다.)
- [ ] CR-02·03: 화면과 내려받은 파일의 모든 결과 줄에 원문 위치, 신뢰도, 가정 여부가 있다.
- [ ] CR-04·05: 원문에 없는 값은 빈칸과 "확인 필요"로 남고, [REDACTED]로 가려진 값은 "값 없음"으로 나온다.
- [ ] CR-06: 팀 가정 값이 들어간 결과(예: 손실 환산)에는 항상 "팀 가정" 표시가 있다.
- [ ] CR-07: 언어 모델이 쓴 문장(일탈·질의 초안, 제안 포인트) 안 숫자가 판정 화면의 근거 값과 같다.
- [ ] CR-08: 어떤 결과도 사람이 확정하기 전에는 "후보"로 표시된다.
- [ ] CR-09: 묶음 C·D 문서는 판정하지 않는다.
- [ ] CR-10: kV를 V로, °F를 °C로 바꾸는 등 단위 환산을 하지 않는다.
- [ ] CR-11: 같은 파일을 키 없이 두 번 등록하면 요약 칸 5개의 숫자가 같다.
- [ ] CR-12: 잘못된 키를 넣으면 정해진 횟수만 다시 시도하고 멈추거나 AI 단계를 건너뛴다. 끝나지 않고 계속 도는지 봅니다.
- [ ] 범위 밖: 가격 계산, 할인, OCR, 경쟁 제품 비교가 어느 화면에도 실제 기능으로 나오지 않는다. 입찰 이력의 금액은 "영업 권한 필요"로 가려져 있다.
