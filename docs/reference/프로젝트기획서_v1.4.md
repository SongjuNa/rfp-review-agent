## 1. 프로젝트 개요

### 1-1. 배경

전력 설비 입찰에서는 발주처가 수백 쪽짜리 RFP를 보냅니다. RFP에는 기술 사양서, 입찰 서식, 장비별 데이터시트, 계약 조건이 섞여 있습니다. 기술 검토 엔지니어는 이 문서를 읽고 세 가지를 해야 합니다.

1. 우리 제품에 걸리는 요구사항을 빠짐없이 찾는다.
2. 우리 제품이 그 요구를 맞추는지 판정한다.
3. 못 맞추는 것은 **일탈 목록**으로, 문서가 애매하거나 값이 서로 다른 것은 **고객 질의 목록**으로 정리해 제출한다.

운영진이 준 실제 RFP 22개(클렌징된 docx, 약 52만 단어, 표 1,360개)를 전부 분석해 보니, 이 일이 어려운 이유가 숫자로 드러났습니다.

| No | 지금 일하는 방식의 어려움 | 데이터에서 확인한 것 |
|---|---|---|
| P1 | **읽을 양이 너무 많다** | 요구사항 후보 줄이 약 11,540줄 (문장 약 7,140 + 데이터시트 칸 약 4,270 + 공급사 답안 134). 가장 긴 문서는 약 21만 단어 |
| P2 | **놓치면 계약 조건이 되는 조항이 숨어 있다** | "일탈 목록에 적지 않은 차이는 받아들인 것으로 본다"(파일 3). "deemed"(~로 본다)만 약 25줄 |
| P3 | **같은 항목인데 값이 다르다** | 가스 누설 0.5 % / 1 %(파일 6 한 문서 안), UPS 10 kVA / 30 kVA(같은 사업의 파일 19·22), 115 kV 최고 전압 125 kV / 123 kV(파일 1) |
| P4 | **숫자끼리 계산이 안 맞는 곳이 있다** | 230 kV 차단기: 차단 전류 50 kA인데 최대 순간 전류 100 kA (계산상 125 kA여야 함). 파일 1·2에 똑같이 반복 |
| P5 | **데이터시트의 40 %는 비교가 아니라 "채우는" 일이다** | 데이터시트 칸 약 4,350개 중 빈칸 약 1,680개(39 %), "규격대로"처럼 규격에 맡긴 칸 약 190개 |
| P6 | **문서 구조를 컴퓨터가 바로 알 수 없다** | 제목 스타일이 없음. 장·절은 번호로만 구분. 한 표가 쪽마다 끊겨 Word 표 4개로 나뉨(파일 1의 115 kV GIS 표) |

엔지니어는 지금 다음 세 가지 방법으로 이 일을 합니다. 방법마다 한계가 있습니다.

| 지금 방식 | 한계 |
|---|---|
| (가) Word·PDF를 직접 읽고 엑셀에 옮겨 적기 | 멀리 떨어진 값끼리 비교하기 어렵고(파일 6의 두 값은 100줄 넘게 떨어짐), 단위를 빼고 숫자만 옮기는 실수가 잦음 |
| (나) Ctrl+F로 단어 검색 | 미리 의심하는 단어만 찾을 수 있음. 같은 뜻의 다른 표현(누설·누기·leakage)을 놓침. 계산 관계는 알 수 없음 |
| (다) 일반 AI 챗봇에 문서를 넣고 질문 | 우리 제품 정보를 모름. 근거 위치가 불안정함. 빈칸에 그럴듯한 값을 지어낼 위험 |

**처리 시간 단축률**처럼 측정하지 않은 숫자는 주장하지 않습니다. 대신 위 표처럼 **데이터로 보이는 일의 양과 놓치기 쉬운 지점**을 근거로 듭니다.

### 1-2. 해결할 문제

> 기술 검토 엔지니어가 수백 쪽 RFP에서 우리 제품에 걸리는 요구사항과 위험·불일치 조건을 빠짐없이 찾고(**지키기**), 우리 제품이 요구보다 나은 점을 근거와 함께 찾아(**내세우기**), 일탈 목록·고객 질의 목록과 기술 제안 포인트를 만들도록 돕는다. [결정]

**왜 "내세우기"까지 하나**: 요구사항을 찾아 요약하는 것만으로는 일반 생성형 AI와 차이가 없습니다. 입찰은 가격만이 아니라 기술적 가치로도 경쟁합니다. 판정 단계에서 이미 요구값과 우리 제품값을 비교하므로, 그 비교에서 **요구보다 나은 점(여유)**을 함께 뽑으면 엔지니어가 고객에게 내세울 근거가 생깁니다.

### 1-3. 프로젝트 목적

1. RFP를 장·절·표·행으로 나누고, 요구사항을 **항목·값·단위·조건·유형·원문 위치**로 정리합니다.
2. 놓치면 손해 보는 **위험 조건**(포괄 조항, 값 불일치, 범위 모호)을 찾아 후보로 보여 줍니다.
3. 요구값과 우리 제품값을 비교해 **준수 / 일탈 후보 / 질의 후보 / 확인 필요 / 보증값 작성** 다섯 가지로 판정합니다.
4. 판정 결과로 **일탈 목록과 고객 질의 목록 초안**을 만들고, 담당자 확인과 승인을 거치게 합니다.
5. 기술 값이 가격에 영향을 주는 곳(변압기 손실 환산)은 **계산까지** 보여 주고, 견적 담당에게 전달합니다.
6. 판정에서 찾은 여유, 손실 환산 우위, 우리 제품의 현장 이력을 모아 **기술 제안 포인트**로 만들고, 엔지니어가 채택한 것만 영업·견적에 전달합니다.

| (선택) | 강점 후보 재현율 | 정답지 대상 절에 "여유 있는 항목" 표시를 더하면 측정 가능. 정답지 작업이 늘어 선택 | — |

### 2-3. 기대효과 (정성)

- 엔지니어가 문서를 처음부터 읽는 대신, **정리된 요구사항 표와 위험 조건 목록에서** 검토를 시작합니다.
- 100줄, 7,000줄 떨어진 값끼리의 충돌(파일 6, 파일 1)처럼 사람이 놓치기 쉬운 곳을 **후보로 먼저** 보여 줍니다.
- 데이터시트 빈칸의 보증값을 근거와 함께 채워, 엔지니어의 반복 입력을 줄입니다.
- 판정마다 **비교한 제품 행과 원문 위치**가 남아, 다른 사람이 이어받아도 같은 기준으로 검토할 수 있습니다.
- 견적·품질·영업 담당이 필요한 줄을 따로 받아, 메일로 손수 골라 보내던 일과 누락이 줄어듭니다.
- 엔지니어는 **위험 조건과 내세울 강점을 원문 위치와 함께 먼저 보고, 판단만** 합니다. 기술 제안서에 쓸 근거(요구보다 나은 값, 손실 환산 우위, 현장 대응 경험)를 다시 찾지 않아도 됩니다.

처리 시간 단축률 같은 정량 효과는 측정하지 않았으므로 주장하지 않습니다.

| 문서 분류 (FR-01) | 규칙 + AI 보조 | 파일명·첫 장으로 묶음·종류·사업 판별, 정정본 쌍 후보 | 규칙과 AI 판단이 다르면 "확인 필요". 판정 대상(묶음 A·B) 문서가 없으면 등록을 거절 [제안] |
| 구조 나누기 (FR-02) | 코드 | 번호 패턴으로 장·절 복원, 끊긴 표 잇기, 반복 머리글 제거 | 번호가 끊긴 곳 표시 |
| 요구사항 추출 (FR-03) | 코드(표 칸) + AI(문장, 절 단위) | 요구사항 줄과 원문 위치 | 원문 위치 대조 |
| 유형 표시 (FR-04) | 규칙표 + AI 보조 | 유형 7종 | 규칙과 AI가 다르면 둘 다 표시 |
| 값 정리 (FR-05) | 코드 | 숫자·단위·조건·기호, 칸 형태, 계산식 | 원문 문자열 보존 |
| 위험 조건 찾기 (FR-06) | 코드(사전·비교) + AI(이유 설명) | 후보와 "왜 다를 수 있는지" 설명 | 후보만 냄, 확정은 사람 |
| 공학 규칙 검산 (FR-12) | 코드 | 최대 순간 전류 규칙 | 규칙 ID 기록 |
| 적합성 판정 (FR-07) | 코드 | 비교 방향 사전으로 판정 5종 | 판정 규칙 ID, 비교 제품 행 기록 |
| 보증값 후보 (FR-08) | 코드 | 항목 → product_master 열 연결 | 없는 값은 비움 |
| 일탈·질의 작성 (FR-09) | AI(문장) + 코드(숫자) | 목록 문장 초안, 숫자는 자리표시자로 넣고 코드가 채움 | 숫자 일치 검사, 누락 점검 |
| 손실 환산 (FR-13) | 코드 | 단가 × 손실값 | 다시 계산해 대조 |
| 현장 이력 연결 (FR-15) | 코드 (연결표 조회) | 요구 항목·제품군으로 고장 사전 조회. 연결표를 만들 때만 의미 검색으로 후보를 뽑고 팀이 확정 | 연결표에 없으면 연결하지 않음 |
| 기술 제안 포인트 (FR-14) | 코드(후보 선정) + AI(문장) | 여유·손실 환산·현장 이력에서 후보, 근거 값만으로 문장 작성 | 근거 칸이 비면 후보를 만들지 않음, 숫자 일치 검사 |
| 오케스트레이터 | 코드 (규칙 분기) | 단계 순서, 재시도, 멈춤 지점 관리 | AI가 분기를 고르지 않음 |
| 담당자 확인·승인 (FR-10) | 사람 | 수정, 확정, 승인, 반려 | 수정 이력 |

v1.2의 그림 1(업무 흐름)과 그림 2(시스템 구성)는 위 표에 맞춰 다시 그려야 합니다 [제안].

### 5-2. AI와 코드와 사람의 역할

| 구분 | 맡는 일 | 맡지 않는 일 |
|---|---|---|
| **AI 언어 모델** | 문장 읽기(요구사항·위험 문장 찾기), 유형 판단 보조, 값 불일치 "이유" 설명, 일탈·질의·**제안 포인트** 문장 초안, 한국어 요약 | 숫자 계산, 판정, 제안 포인트 후보 고르기, 분기 선택, 확정, 빈칸 값 만들기 |
| **코드** | 구조 나누기, 값 정리, 계산식 계산, 적합성 판정·여유 계산, 공학 규칙, 손실 환산, 제안 포인트 후보 선정, 연결표 조회, 숫자 일치 검사, 분기 | 문장의 뜻 해석 |
| **사람** | 판정 수정, 일탈·질의 확정, 보증값 확정, 제안 포인트 채택·버림, 승인, 제출 | — |

**근거 묶음**: 시스템이 만드는 모든 값은 `{값, 원문 위치, 신뢰도, 가정 여부}`를 함께 저장합니다. 원문 위치가 없는 값은 결과로 내보내지 않고 "확인 필요"로 둡니다.

**긴 문서 처리**: 문서를 통째로 넣지 않고, 구조 나누기로 절을 나눈 뒤 절마다 처리합니다.

**언어**: 추출은 원문 언어 그대로 합니다. 화면과 산출물은 한국어 요약에 원문을 함께 적습니다.

- **product_master 기준** [결정]: 판정은 LS 카탈로그의 **정격별 행**으로 합니다. 예: GIS 145 kV 40 kA, 245 kV 50 kA, VCB 24 kV 25 kA 630 A. 판정에 쓰는 정격만 행으로 나누고, 판정에 쓰지 않는 품목(미국 묶음의 UL VCB, SPD)은 대표 1행만 둡니다.
- **인증서** [결정]: GIS 인증서·시험성적서 28건은 product_master의 certifications 칸에 문장으로 넣었습니다. 만료 여부 자동 판정은 하지 않습니다.
- **국제 규격 원문**은 유료라 없습니다. "As per IEC"처럼 규격에 맡긴 요구는 값을 찾지 않고 "확인 필요"로 모읍니다.
- 가정 값은 화면과 산출물에 항상 "팀 가정" 표시를 붙입니다.
- **강점 방향**: 모든 여유가 강점은 아닙니다. 단시간 전류·내전압은 클수록 좋지만, 무게·크기는 크면 불리합니다. 그래서 비교 방향 사전 39줄마다 "강점 방향(클수록 좋음 / 작을수록 좋음 / 강점 아님)" 칸을 더합니다.
- **현장 이력 연결의 한계** (발표에서 먼저 말함)
  - 제품군 단위 연결만 가능합니다. 프로젝트 1 데이터는 12 kV 개폐기·1,000 kVA 변압기 수준이고, 이번 RFP는 115~245 kV입니다. GIS는 프로젝트 1 데이터에 없습니다. 그래서 "같은 종류의 장비에서 이런 현장 이슈가 있었다"까지만 말합니다.
  - 프로젝트 1 데이터에는 운영진이 의도한 오류가 있습니다. 연결표에 넣을 고장은 원인·조치를 확인하고 넣습니다.
  - 고객사의 품질 이력이 아니라 **우리 제품의 현장 이력**입니다.
  - 예: 파일 4(고압 개폐기 사양서)의 "제어반마다 결로 방지 히터, 온도조절기로 제어" 요구 ↔ 고장 사전 FLT-051 "결로 방지 히터가 꺼져 결로 → 부분방전 경보"(해결 사례 있음). 결로·히터 관련 문구는 22개 RFP 중 14개에 있습니다.

## 6. 견적 연결·강점 제안과 승인 기준

### 6-1. 견적 연결: 손실 환산 계산 [결정]

가격 자료(단가표·원가)는 받지 못했습니다. 그래서 **가상 단가 계산과 할인 공식은 뺐습니다.** v1.2의 할인 공식은 이전 합성 데이터에서 찾은 것이라 이번 RFP 데이터에는 근거가 없었습니다.

대신 **기술 값이 가격을 바꾸는 곳**을 계산으로 보여 줍니다. 파일 1에는 "입찰자를 비교할 때 변압기 손실 1 kW당 정해진 금액을 곱해 입찰 가격에 더한다"는 조항이 있습니다 (8236~8241행).

| 손실 종류 | 발주처 단가 ($/kW) | 손실값 (kW, **팀 가정**) | 평가 가산 ($) |
|---|---|---|---|
| 무부하 손실 | 4,500 | 60 | 270,000 |
| 부하 손실 | 3,200 | 300 | 960,000 |
| 보조 손실 | 1,300 | 8 | 10,400 |
| 합계 | | | **1,240,400** |

- 계산은 AI가 아니라 코드가 하고, 계산식을 화면에 그대로 보여 줍니다.
- 손실값은 변압기 카탈로그에도 없어 계속 **팀 가정**입니다. 손실값을 바꾸면 결과가 다시 계산됩니다.
- 결과는 견적 담당에게 "비용 영향" 유형으로 전달합니다.
- **손실 환산 우위**: 손실이 적은 제품은 기기 값이 조금 비싸도 평가 가격에서 이길 수 있습니다. 기술이 가격이 되는 지점입니다. 그래서 계산 결과를 기술 제안 포인트(FR-14)로도 넘깁니다. 손실값이 팀 가정인 동안은 "팀 가정" 표시를 붙인 채로만 보여 줍니다.

### 6-2. 기술 제안 포인트 [결정]

| 유형 | 무엇을 찾나 | 근거 | 예 |
|---|---|---|---|
| 요구보다 나은 값 | 판정이 준수이고, 여유가 강점 방향인 항목 | 요구 원문 위치 + product_master 행 | 요구 40 kA(1초) ↔ GIS-145 40 kA(3초) → 시간 3배 |
| 손실 환산 우위 | 손실 환산 가산액이 기준보다 작은 경우 | RFP 손실 환산 조항 + 손실값(팀 가정) | 무부하·부하·보조 손실 × 단가 |
| 현장 경험 | 요구 항목이 우리 현장 이력과 연결되는 경우 | 요구–고장 연결표 + 고장 사전 | 결로 방지 히터 요구 ↔ FLT-051 |

- 후보 선정은 코드가 합니다. 처음에는 "여유가 있고 강점 방향이면 모두 후보"로 시작하고, 엔지니어가 거릅니다.
- AI는 **근거 값만으로** 제안 문장을 씁니다. 근거 칸(요구 원문 위치, 제품 행)이 비어 있으면 후보를 만들지 않습니다.
- 경쟁 제품과의 비교는 하지 않습니다 (보류).

### 6-3. 승인 기준 [결정]

  - 파일 6의 가스 누설 관련 절 2곳 (값 불일치, 질의)
  - 파일 3의 6장 "CLARIFICATION, EXCEPTION AND DEVIATION" (포괄 조항)
- 추적표 v3의 15개 사례마다 적힌 "정답지" 줄을 출발점으로 씁니다.

**보완 방법**

| 방법 | 내용 |
|---|---|
| 정답 작성 기준서 | "요구사항 1줄"의 단위, 값·단위 적는 법, 판정 5종 적용 기준을 먼저 정함 |

## 부록 D. 용어

| 용어 | 뜻 |
|---|---|
| RFP | 발주처가 "이런 조건으로 사겠다"며 보내는 요청 문서 묶음 |
| 요구사항 | "~해야 한다"로 적힌 조건 한 개. 데이터시트의 요구값 칸도 포함 |
| 데이터시트 | 장비마다 "항목 / 단위 / 발주처 요구값 / 공급사 보증값" 칸으로 된 표 |
| 보증값 | 공급사가 "우리 제품은 이 값을 보장한다"고 적어 내는 값 |
| 적합성 판정 | 요구값과 제품값을 비교해 맞는지 보는 일 |
| 준수 | 요구를 맞춤 |
| 일탈 (Deviation) | 요구는 분명한데 우리 제품이 그대로 못 맞춰, 다르게 공급하겠다고 미리 밝히는 것 |
| 질의 (Clarification) | 문서가 애매하거나 값이 서로 달라 고객에게 묻는 것 |
| 확인 필요 | 비교할 값이 없거나 경계값이라 사람이 봐야 하는 것 |
| 포괄 조항 | "목록에 없는 차이는 받아들인 것으로 본다"처럼 공급사에게 불리하게 넓게 적힌 조항 |
| 규격 위임 | 값을 직접 적지 않고 "국제 규격대로(As per IEC)"라고 규격에 맡긴 요구 |
| 공급 범위 | 공급사가 책임지고 공급해야 하는 항목 |
| 손실 환산 | 변압기 손실(kW)에 발주처가 정한 단가($/kW)를 곱해 입찰 평가 가격에 더하는 계산 |
| product_master | 우리 제품의 기준 정보를 모은 표 |
| 설계 사례 카드 | 특정 사업에 맞춘 설계 값을 담은 참고용 제품 행 |
| GIS | 차단기 등을 절연 가스를 채운 금속 통에 넣은 고압 개폐장치 |
| 단시간 전류 / 최대 순간 전류 | 사고 때 몇 초 동안 견뎌야 하는 큰 전류 / 사고 직후 첫 순간 치솟는 꼭짓값 |
| 근거 묶음 | 값과 함께 저장하는 원문 위치·신뢰도·가정 여부 |
| 숫자 일치 검사 | AI가 쓴 문장 속 숫자가 근거 값과 같은지 코드로 확인하는 것 |
| 팀 가정 | 실제 자료가 없어 팀이 만든 값 |
| 여유 | 제품값이 요구값보다 나은 정도 (예: 요구 1초, 제품 3초 → 시간 3배) |
| 강점 방향 | 그 항목에서 여유가 강점이 되는 방향 (클수록 좋음 / 작을수록 좋음 / 강점 아님) |
| 기술 제안 포인트 | 고객에게 내세울 강점 후보. 근거(요구 원문 위치, 제품 행)가 있어야 만듦 |
| 현장 이력 | 우리 제품군에서 실제로 있었던 고장과 조치 기록 (프로젝트 1 고장 사전) |
