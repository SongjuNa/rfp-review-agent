# 설계: add-document-processors

## 결정

### 1. 처리기 표 (`pipeline/processors.py`)
```
Processor(kind, name, hint, check)
BID_FORM          입찰 서식    hint: 가격표·데이터시트 묶음. 표 칸 값과 제출 서식 안내가 많다     check: 표 칸(TABLE_CELL) 요구사항 0줄
REQUIREMENT_SPEC  요구 사양서  hint: 기술 요구 사양. shall·must 요구 문장이 많다              check: 요구사항(REQUIREMENT) 0줄
TEST_SPEC         시험 사양서  hint: 시험 항목·입회·성적서 요구가 많다                         check: 시험(TEST) 유형 줄 0
PURCHASE_SPEC     구매 요청서  hint: 공급 범위·수량·납기·상업 조건이 많다                      check: 요구사항 0줄
SUPPLIER_SPEC     공급사 사양서 hint: 공급사 답안. 조항마다 C/D/E 준수 표시가 있다              check: C/D/E 표시 0줄
UNKNOWN           일반          hint 없음                                                     check 없음
```
- 문장은 [제안]이고 표 한 곳만 고치면 된다. 점검은 문서 저장이 끝난 뒤 같은 트랜잭션 안에서 DB 건수로 센다.
- 판독 불가 문서·다시 쓴(재사용) 문서는 점검하지 않는다(재사용 문서는 처음 처리 때 기록이 남아 있다).

### 2. AI 질문에 문서 종류 설명
- `tasks.label_sections`·`type_unclassified`에 `doc_hint`(없으면 None)를 더해 프롬프트 첫 줄에 "문서 종류: …"를 넣는다. 답 형식·검사는 그대로.
- `PROMPT_VERSION` p4 → p5. 처리 판이 바뀌어 같은 파일도 새로 분석한다(K13 전후 채점 가능).

### 3. 점검 뒤 한 번 다시 처리
- `_process_new`를 처리기 인자로 돌린다. 점검에 걸리고 AI가 있고 처리기가 일반이 아니면, 그 문서의 트랜잭션을 되돌리고(`Rollback` 예외) 일반 처리기로 한 번 더 돈다. 두 번째 점검 결과와 관계없이 그 결과를 쓴다(한 번만).
- 문서 행에 `processor`(마지막에 쓴 처리기), `process_check`(첫 점검에 걸린 이유, 없으면 NULL), `reprocessed`를 남기고, 걸렸으면 `needs_review = true`. 마이그레이션 0030.
- 다시 처리하면 AI 호출이 그 문서만큼 늘어난다. 실행 기록 `documents_reprocessed`로 보인다.

### 4. 문서 병렬 처리
- `documents` 노드가 문서를 `RFP_DOC_WORKERS`(기본 2)개 스레드로 처리한다. 스레드마다 같은 DB로 연결을 새로 연다(`conn.info.dsn` + `password`). 1이면 지금처럼 같은 연결로 차례로.
- **같은 요구 묶기**: 병렬일 때는 문서 처리 중 다른 문서를 찾아 묶지 않고(`dedup_of` 비움), 모두 끝난 뒤 올린 순서대로 묶는다. 대표는 이 검토 밖의 예전 문서가 먼저(요구 번호 순), 그다음 이 검토에서 앞에 올린 문서. 차례로 처리할 때와 같은 대표가 된다. 대표 요구에 위치를 더하는 것도 같다(CR-03).
- **새 파일 번호**: 목록에 없는 새 문서의 번호(101번부터)는 시작 전에 올린 순서대로 미리 정해 둔다. 목록 문서·예전 번호가 있는 문서는 그 번호를 쓰므로 미리 정한 번호는 비어 남을 수 있다.
- 한 문서가 실패하면 나머지 문서는 끝까지 처리(저장)한 뒤 올린 순서로 첫 오류를 낸다. 다시 시도하면 저장한 문서는 다시 쓴다(NFR-05). 취소는 스레드마다 진행 기록 때 멈춘다.
- 세부 진행은 처리 중인 문서마다 번갈아 적힌다(화면은 마지막 값만 보인다) [확인 필요].

## 대안
- 처리기마다 다른 추출 규칙: 이번 범위 밖(결정).
- 점검에 걸리면 AI가 고른 다른 종류로 다시 처리: 종류를 AI가 고르는 셈이라 버림(CR-01). 사람이 종류를 고치면 그 종류로 다시 분석된다(processing_key에 사람 분류).
- 프로세스 병렬(multiprocessing): DB 연결·AI 객체 공유가 어려워 버림. AI 요청은 입출력 대기라 스레드로 충분하다.

## 위험
- AI 동시 요청이 문서 수 × `RFP_LLM_WORKERS`(기본 2 × 4 = 8)까지 는다. 요청 한도에 걸리면 `RFP_DOC_WORKERS=1`.
- 병렬 결과가 차례 결과와 같은지 테스트로 지킨다(요구 줄·같은 요구 묶기·판정 수).
