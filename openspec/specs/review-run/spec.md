# review-run Specification

## Purpose
RFP 검토 한 번을 하나의 실행으로 묶어, 결과가 어떤 입력·사전·제품표에서 나왔는지 추적하고 같은 입력이면 같은 결과를 내게 한다.

## Requirements

### Requirement: 실행 생성
시스템은 검토를 시작할 때 실행 하나를 만들고 대상 문서, 시작한 사람, 사전·제품표 판을 기록해야 한다(SHALL). 이 실행에서 나온 모든 결과는 실행에 묶여야 한다(SHALL).

#### Scenario: 파일 1로 검토 시작
- **WHEN** 엔지니어가 파일 1로 검토를 시작하면
- **THEN** 실행 하나가 PROCESSING 단계로 생기고 사전 판이 기록된다

### Requirement: 재현성
시스템은 같은 문서·같은 사전 판·같은 제품표로 다시 실행하면 숫자와 판정 결과가 같아야 한다(SHALL, CR-11, NFR-02).

#### Scenario: 같은 문서 두 번
- **WHEN** 같은 문서를 같은 사전 판으로 두 번 처리하면
- **THEN** 두 실행의 요구사항 수, 값, 위험 조건 후보가 같다

### Requirement: AI 오류 처리
시스템은 AI 응답 오류나 시간 초과에 정해진 횟수만 재시도하고, 그래도 실패하면 실행을 멈추고 "처리 실패 — 다시 시도"를 알려야 한다(SHALL, CR-12).

#### Scenario: AI 키 없음
- **WHEN** 언어 모델 키 없이 검토를 실행하면
- **THEN** AI 보조 단계는 건너뛰고 코드 규칙 결과로 엔지니어 검토(ENGINEER_REVIEW) 단계까지 간다

#### Scenario: 계속 실패
- **WHEN** AI 호출이 재시도 횟수를 넘겨 실패하면
- **THEN** 실행은 FAILED가 되고 실패한 단계와 "처리 실패 — 다시 시도"가 보인다

### Requirement: 긴 문서는 절 단위로 처리
시스템은 문서를 통째로 AI에 넣지 않고 절 단위로 처리하며, 처리한 절의 결과를 저장해 재사용해야 한다(SHALL, NFR-05). 저장된 결과는 처리 판과 파일 내용이 모두 같을 때만 다시 써야 하며, 파일 이름이나 파일 번호가 같아도 내용이 다르면 새로 처리해야 한다(SHALL, CR-11). 같은 파일을 여러 검토가 거의 동시에 처리해 저장이 겹치면 늦은 쪽은 먼저 저장된 결과를 다시 쓰고 멈추지 않아야 한다(SHALL).

#### Scenario: 가장 긴 문서
- **WHEN** 파일 2를 처리하면
- **THEN** 처리가 끝나고 AI 호출 입력은 모두 절 단위이다

#### Scenario: 이름이 같고 내용이 다른 파일
- **WHEN** 파일 목록의 같은 이름으로 내용이 다른 두 파일을 차례로 검토하고, 두 번째 파일로 한 번 더 검토하면
- **THEN** 두 파일은 같은 파일 번호이지만 두 번째 파일은 새로 처리되고, 세 번째 검토는 두 번째 처리 결과를 다시 쓴다

#### Scenario: 같은 파일을 거의 동시에 두 번 올림
- **WHEN** 두 검토가 같은 파일을 같은 처리 판으로 처리하다 저장이 겹치면
- **THEN** 늦은 검토는 새 문서를 만들지 않고 먼저 저장된 문서로 판정까지 끝난다

### Requirement: 검토 정보
시스템은 실행마다 사람이 입력한 검토 정보(사업명, 검토명, 고객사, 국가, 제출 마감일, 담당 엔지니어)를 저장하고 검토를 시작할 때와 시작한 뒤에 받을 수 있어야 한다(SHALL). 모든 칸은 비어 있어도 되며, 시스템이나 언어 모델이 빈칸을 채우지 않아야 한다(MUST NOT, CR-04). 담당 엔지니어가 비어 있고 시작한 사람이 엔지니어 역할이면 그 사람으로 둔다. 담당 엔지니어는 엔지니어 역할 사용자만 될 수 있다(SHALL).

#### Scenario: 검토 정보와 함께 시작
- **WHEN** 엔지니어가 사업명 "Thai Binh", 검토명 "115·230 kV GIS 변전소 신설", 고객사, 국가, 마감일 2026-10-30을 넣고 파일 1로 검토를 시작하면
- **THEN** 실행 요약에 다섯 값이 그대로 보이고 담당 엔지니어는 시작한 엔지니어다

#### Scenario: 검토 정보 없이 시작
- **WHEN** 검토 정보를 하나도 넣지 않고 검토를 시작하면
- **THEN** 실행은 그대로 시작되고 검토 정보 칸은 모두 비어 있다

#### Scenario: 엔지니어가 아닌 담당자
- **WHEN** 견적 담당 사용자를 담당 엔지니어로 넣으면
- **THEN** 담당 엔지니어는 엔지니어만 될 수 있다는 오류가 나고 바뀌지 않는다

### Requirement: 검토 정보 고치기와 이력
시스템은 실행 단계와 관계없이 검토 정보를 고치게 하고, 고칠 때마다 이전 값·새 값·작업자·시각을 수정 이력에 남겨야 한다(SHALL). 검토 정보는 판정·후보 계산에 쓰지 않아야 한다(MUST NOT).

#### Scenario: 마감일을 바꿈
- **WHEN** 엔지니어가 마감일을 2026-10-30에서 2026-11-02로 고치면
- **THEN** 실행 요약의 마감일이 바뀌고 이력 1건(이전 값, 새 값)이 남는다

#### Scenario: 판정은 그대로
- **WHEN** 검토명과 고객사를 고친 뒤 판정 목록을 다시 보면
- **THEN** 판정 줄 수와 결과가 고치기 전과 같다

### Requirement: 실행 목록 응답
시스템은 실행 목록과 실행 요약에 검토 번호(`RV-<시작 연도>-<실행 번호 세 자리>`), 검토 정보, 담당 엔지니어 이름을 넣고, 실행 목록에는 요구사항·위험 조건·일탈 후보·제안 포인트 개수를 함께 넣어야 한다(SHALL).

#### Scenario: 목록의 개수
- **WHEN** 처리가 끝난 실행이 있는 상태에서 실행 목록을 부르면
- **THEN** 그 줄의 요구사항·위험 조건·일탈 후보·제안 포인트 개수가 실행 요약의 개수와 같다

#### Scenario: 검토 번호
- **WHEN** 2026년에 시작한 실행 25번을 부르면
- **THEN** 검토 번호는 "RV-2026-025"다

### Requirement: 목록 API의 전체 개수
시스템은 나눠서 주는 목록(요구사항, 판정, 보증값 후보)에 거름 조건을 적용한 전체 개수를 함께 알려야 한다(SHALL).

#### Scenario: 판정 목록 나눠 받기
- **WHEN** 일탈 후보만 거르고 10줄씩 판정 목록을 부르면
- **THEN** 10줄 이하가 오고 일탈 후보 전체 개수가 함께 온다

### Requirement: 판정 목록 거르기와 판정 순서
시스템은 판정 목록을 주 유형, 검색어(항목 이름·영문 항목명·원문 문장), 확정 안 한 것만으로 거르고, 요청하면 판정 순서(일탈 후보 → 질의 후보 → 확인 필요 → 작성 필요 → 준수, 같은 판정 안에서는 판정 번호 순)로 정렬해야 한다(SHALL). 걸러진 전체 개수는 지금처럼 함께 알려 준다. 판정 줄에는 주 유형 코드와 이름을 넣는다(SHALL).

#### Scenario: 확정 안 한 일탈 후보만
- **WHEN** 일탈 후보 4건 중 1건을 확정한 실행에서 일탈 후보이면서 확정 안 한 판정만 요청하면
- **THEN** 3건이 오고 전체 개수도 3이다

#### Scenario: 판정 순서로 받기
- **WHEN** 판정 순서로 목록을 요청하면
- **THEN** 일탈 후보가 모두 질의 후보보다 앞에 오고, 준수는 맨 뒤에 온다

#### Scenario: 검색어로 거르기
- **WHEN** 검색어 "busbar"로 요청하면
- **THEN** 영문 항목명에 busbar가 들어간 판정만 온다

### Requirement: 판정 칩 건수
시스템은 실행의 현재 판정을 판정 값마다 센 건수, 확정 안 한 판정 수, 그중 준수 수를 한 번에 알려 줘야 한다(SHALL). 반려한 판정은 세지 않는다.

#### Scenario: 칩 건수
- **WHEN** 판정 칩 건수를 요청하면
- **THEN** 판정 값마다의 건수 합이 전체 판정 수와 같고, 확정 안 한 수는 확정·수정한 판정을 뺀 수다

### Requirement: 위험 조건 항목 이름
시스템은 위험 조건 목록의 값 불일치 줄에 표준 항목의 한국어 이름을 함께 넣어야 한다(SHALL). 항목이 없는 위험 조건(포괄 조항, 범위 모호)은 이름을 비워 둔다.

#### Scenario: 값 불일치 항목 이름
- **WHEN** 가스 누설률 값이 문서마다 다른 실행의 위험 조건 목록을 요청하면
- **THEN** 값 불일치 줄의 항목 이름은 "가스 누설률"이고, 포괄 조항 줄의 항목 이름은 비어 있다

### Requirement: 손실 환산 종류별 가산액
시스템은 손실 환산 목록에 무부하·부하·보조마다 단가 × 손실값으로 계산한 가산액과 단가 행의 원문 위치를 함께 넣어야 한다(SHALL). 손실값이 없는 종류의 가산액과, 단가 단위가 $/kW가 아닌 경우의 가산액은 비워 둔다(CR-10).

#### Scenario: 종류별 가산액과 단가 위치
- **WHEN** 단가 4,500·3,200·1,300 $/kW 행이 있고 손실값을 60·300·8 kW로 넣은 실행의 손실 환산 목록을 요청하면
- **THEN** 종류별 가산액은 270,000·960,000·10,400이고 그 합이 가산액 합계와 같으며, 단가 행 위치 3개가 함께 온다

### Requirement: 이력 대상 이름
시스템은 실행의 수정 이력 줄마다 바뀐 대상의 이름을 함께 넣어야 한다(SHALL). 판정·보증값은 항목 이름(없으면 영문 항목명), 위험 조건은 표현(없으면 항목 이름), 제안 포인트는 근거, 일탈·질의 목록은 문장 앞부분, 손실 환산은 비교 제품이다. 검토 실행과 비교 제품 바꾸기 줄은 비워 둔다.

#### Scenario: 이력 대상 이름
- **WHEN** 질의 후보 판정을 준수로 바꾸고, 다른 실행에서 포괄 조항 위험 조건을 문제 없음으로 닫은 뒤 이력을 요청하면
- **THEN** 판정 줄의 대상 이름은 그 판정의 항목 이름이고, 위험 조건 줄의 대상 이름은 그 표현이다

### Requirement: 문서 읽기 점검 목록
시스템은 실행마다 시스템이 제대로 읽지 못한 곳을 점검 줄로 돌려줘야 한다(SHALL). 종류는 표(칸 역할을 못 찾은 표), 그림(문서 안 그림, 읽지 않은 스캔 문서), 단위(단위 없는 값을 표나 절마다 묶음), 위치(번호가 끊긴 절, 같은 문서에서 번호가 두 번 나온 절)이고, 줄마다 종류, 무엇, 파일, 위치, 문제, 할 일, 확인한 사람과 시각을 넣는다. 같은 입력이면 같은 줄이 같은 순서로 나온다(CR-11).

#### Scenario: 읽지 못한 곳 목록
- **WHEN** 칸 역할을 못 찾은 표, 그림 1개, 단위 없는 값, 같은 번호가 두 번 나온 절이 있는 문서로 실행하고 점검 목록을 요청하면
- **THEN** 표·그림·단위·위치 줄이 이 순서로 오고, 각 줄에 파일 이름과 줄 번호가 든 위치와 할 일이 있으며 확인한 사람은 비어 있다

### Requirement: 문서 읽기 점검 확인
시스템은 엔지니어가 담당자 확인 단계에서 점검 줄을 "직접 확인함"으로 표시하거나 되돌릴 수 있게 하고, 두 동작을 모두 수정 이력에 남겨야 한다(SHALL). 승인 화면 정보에는 확인하지 않은 점검 줄 수를 넣는다.

#### Scenario: 점검 확인과 되돌리기
- **WHEN** 엔지니어가 점검 줄 하나를 확인했다가 되돌리면
- **THEN** 확인했을 때는 그 줄에 확인한 사람과 시각이 있고 확인 안 한 수가 1 줄며, 되돌리면 다시 비고, 이력에 두 줄이 그 점검 줄 이름으로 남는다

#### Scenario: 담당자 확인 단계에서만 확인
- **WHEN** 결재 상신한 실행의 점검 줄을 확인하려 하면
- **THEN** 409 오류로 거절한다

### Requirement: 처리 세부 진행 기록
시스템은 처리 중인 실행의 문서 읽기 단계에서 지금 하는 세부 일(문서 종류 확인, 절·표 나누기, 요구사항 뽑기, AI 문장 구분, 저장, AI 유형 붙이기), 몇 번째 파일인지, AI 일은 끝난 줄 수와 전체 줄 수를 처리 도중에 바로 기록해야 한다(SHALL). 단계나 세부 진행이 바뀔 때마다 마지막 진행 시각을 기록하고, 단계가 바뀌면 세부 진행을 지운다. 진행 기록이 실패해도 처리는 계속한다. 실행 요약과 실행 목록은 세부 진행과 마지막 진행 시각을 함께 준다. 판정·추출 결과는 바뀌지 않는다(CR-11). [제안]

#### Scenario: 유형 붙이기 진행 개수
- **WHEN** 규칙으로 유형을 정하지 못한 요구사항이 있는 문서를 AI와 함께 처리하면
- **THEN** 처리 도중 "AI 유형 붙이기" 세부 진행이 기록되고, 끝난 줄 수는 0보다 크고 전체 줄 수 이하이며 마지막 기록에서 전체 줄 수와 같고, 파일 순번은 1 / 1이다

#### Scenario: 단계가 바뀌면 세부 진행을 지움
- **WHEN** 처리가 끝난 실행의 실행 요약을 부르면
- **THEN** 세부 진행은 비어 있고 마지막 진행 시각이 있다

#### Scenario: 목록에도 세부 진행
- **WHEN** 문서 읽기 단계에서 유형 붙이기 120 / 400줄까지 기록된 실행이 있을 때 실행 목록을 부르면
- **THEN** 그 줄의 세부 진행은 AI 유형 붙이기, 120, 400이다

### Requirement: 검토 취소
시스템은 처리 중인 검토에 사람의 취소 요청을 받아 요청 시각과 요청자를 남기고, 처리 흐름이 다음 진행을 기록할 때 멈추게 해야 한다(SHALL). 멈춘 검토는 처리 실패가 되고 멈춘 단계와 "○○이(가) 분석을 취소했습니다" 문장을 남긴다. 멈춘 문서의 반쯤 만든 결과는 저장하지 않는다. 마지막 진행이 10분 넘게 없으면 요청 즉시 처리 실패로 바꾼다. 처리 중이 아닌 검토의 취소 요청은 거절한다. [제안]

#### Scenario: 처리 중 취소
- **WHEN** 문서 읽기 단계를 처리하는 중인 검토에 취소를 요청하면
- **THEN** 처리가 다음 진행 기록에서 멈추고 검토는 처리 실패, 멈춘 단계 문서 읽기, 취소 문장과 취소 표시가 남으며 그 문서는 저장되지 않는다

#### Scenario: 멈춘 검토 취소
- **WHEN** 마지막 진행이 11분 전인 처리 중 검토에 취소를 요청하면
- **THEN** 바로 처리 실패가 되고 "진행이 멈춰" 문장이 남는다

#### Scenario: 끝난 검토는 취소 못 함
- **WHEN** 담당자 확인 단계인 검토에 취소를 요청하면
- **THEN** 409 오류로 거절하고 검토는 그대로다

### Requirement: 검토 다시 시도
시스템은 처리 실패한 검토(취소 포함)에 사람의 다시 시도 요청을 받아, 처음 시작할 때와 같은 파일과 같은 사람 분류로 같은 검토를 다시 처리해야 한다(SHALL). 이미 처리한 문서는 다시 쓰고(NFR-05) 다른 결과는 다시 만든다. 다시 시도하면 처리 중으로 바뀌고 멈춘 단계·오류 문장·취소 표시를 지우며 다시 시도 횟수를 하나 늘린다. 처리 실패가 아니거나 다시 돌릴 파일 정보가 없으면 거절한다. [제안]

#### Scenario: 취소한 검토 다시 시도
- **WHEN** 문서 읽기에서 취소한 검토를 다시 시도하면
- **THEN** 같은 검토 번호로 담당자 확인 단계까지 가고 판정이 나오며 다시 시도 횟수는 1이다

#### Scenario: 처리한 문서는 다시 씀
- **WHEN** 문서 두 개 가운데 첫 문서를 처리한 뒤 실패한 검토를 다시 시도하면
- **THEN** 첫 문서는 같은 문서로 다시 쓰이고 새 문서 줄은 두 번째 문서 하나만 생긴다

#### Scenario: 다시 돌릴 파일 정보 없음
- **WHEN** 파일 정보가 저장되지 않은 처리 실패 검토를 다시 시도하면
- **THEN** 409 오류와 다시 등록하라는 안내가 돌아오고 검토는 그대로다
