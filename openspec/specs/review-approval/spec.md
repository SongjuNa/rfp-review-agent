# review-approval Specification

## Purpose
시스템이 낸 후보를 사람이 확정·수정·반려하고, 승인 기준에 걸리면 승인자를 거치게 해서, 사람이 확인하지 않은 결과가 나가지 않게 한다 (FR-10).

## Requirements

### Requirement: 멈춤 지점
시스템은 처리를 마친 실행을 담당자 확인 단계에서 멈추고, 엔지니어가 결재 상신하면 승인 기준(AR-01·02·03·06·07·08)을 판단해 걸린 기준을 기록한 뒤 걸린 기준이 없어도 승인 단계에서 멈춰야 한다(SHALL). 결재자의 결정 없이 승인됨이 되지 않아야 한다(MUST NOT) [결정 2026-10-28: 명세서 [결정] "걸린 기준이 없으면 바로 승인됨"을 바꿈]. AR-03의 확인 필요 비율은 보증값 후보를 채운 칸과 제품표에 연결되지 않은 보증값 빈칸(직접 작성할 칸)을 빼고 계산한다(SHALL) [결정 2026-11-01].

#### Scenario: 일탈 후보가 있는 실행
- **WHEN** 일탈 후보가 1건 이상인 실행을 결재 상신하면
- **THEN** 실행은 승인 대기가 되고 걸린 기준은 AR-01이다

#### Scenario: 걸린 기준이 없는 실행
- **WHEN** 승인 기준에 하나도 걸리지 않는 실행을 결재 상신하면
- **THEN** 실행은 승인 대기가 되고 걸린 기준 목록은 비어 있다

#### Scenario: 승인 대기 중 수정
- **WHEN** 승인 대기인 실행의 후보를 고치려 하면
- **THEN** 담당자 확인 단계에서만 된다는 오류가 나고 바뀌지 않는다

#### Scenario: 확인 필요 비율
- **WHEN** 보증값 후보를 채운 칸을 뺀 "확인 필요" 비율이 20 %를 넘으면
- **THEN** 걸린 기준에 AR-03이 들어간다 [제안]

#### Scenario: 직접 작성할 칸은 비율에서 뺌
- **WHEN** 판정 줄 대부분이 제품표에 연결되지 않은 보증값 빈칸인 실행의 승인 화면을 부르면
- **THEN** 확인 필요 비율의 확인 필요 수와 전체 수에 그 칸이 들어가지 않고, 직접 작성할 칸 수가 그 칸 수와 같으며, 그 칸 때문에 AR-03이 걸리지 않는다

#### Scenario: 의심할 빈칸은 그대로 셈
- **WHEN** 제품을 고르지 못해 보증값이 빈 칸이 있는 실행의 승인 화면을 부르면
- **THEN** 그 칸은 확인 필요 수에 들어가고 직접 작성할 칸 수에는 들어가지 않는다

### Requirement: 수정 이력
시스템은 판정·목록·보증값·제안 포인트·위험 조건에 대한 확정·수정·반려·채택·버림을 대상, 이전 값, 새 값, 사유, 작업자, 시각과 함께 기록해야 한다(SHALL). 수정·반려·버림에는 사유가 필요하다. 확정 뒤 수정하면 관련 목록을 다시 만들고 누락 점검을 다시 해야 한다(SHALL).

#### Scenario: 판정을 바꿈
- **WHEN** 엔지니어가 판정을 "준수"에서 "일탈 후보"로 바꾸면
- **THEN** 이력 1건(이전 값, 새 값, 사유)이 남고 일탈 목록이 다시 생성된다

### Requirement: 채택한 제안 포인트만 전달
시스템은 기술 제안 포인트에 채택 / 버림 / 수정을 기록하고, 채택한 것만 전달 대상으로 삼아야 한다(SHALL, AR-08).

#### Scenario: 2건 중 1건 채택
- **WHEN** 제안 포인트 2건 중 1건을 채택하면
- **THEN** 채택한 1건만 전달 대상이다

### Requirement: 승인 결정
시스템은 상신 때 지정된 결재자만 승인 또는 반려하고 의견을 남기게 하고, 결정 전에는 실행을 승인됨으로 바꾸지 않아야 한다(MUST NOT). 반려에는 의견이 필요하다(SHALL).

#### Scenario: 반려
- **WHEN** 지정된 결재자가 의견과 함께 반려하면
- **THEN** 실행은 반려됨이 되고 의견과 시각이 기록된다

#### Scenario: 승인자가 아닌 사용자
- **WHEN** 승인자 역할이 아닌 사용자가 승인하려 하면
- **THEN** 거부되고 실행은 승인 대기로 남는다

#### Scenario: 지정되지 않은 승인자
- **WHEN** 승인자 역할이지만 상신 때 지정되지 않은 사용자가 승인하려 하면
- **THEN** 지정된 결재자만 결정할 수 있다는 오류가 나고 실행은 승인 대기로 남는다

### Requirement: 결재 상신
시스템은 담당자 확인 단계의 실행을 결재 상신할 때 결재자 1명(승인자 역할)과 상신 의견을 받아, 상신한 사람·시각·결재자·의견·걸린 기준을 기록하고 수정 이력에 남겨야 한다(SHALL). 결재자나 상신 의견이 없으면 상신하지 않아야 한다(MUST NOT). 걸린 기준이 남아 있어도 상신할 수 있다.

#### Scenario: 결재자와 의견을 넣고 상신
- **WHEN** 엔지니어가 결재자로 승인자 1명을 고르고 상신 의견 "질의 1건은 10-27 회신 예정"을 넣어 상신하면
- **THEN** 실행은 승인 대기가 되고 승인 화면에 상신한 사람, 상신 시각, 결재자, 상신 의견, 걸린 기준이 보인다

#### Scenario: 상신 의견 없이 상신
- **WHEN** 상신 의견을 비우고 상신하면
- **THEN** 상신 의견이 필요하다는 오류가 나고 실행은 담당자 확인 단계로 남는다

#### Scenario: 승인자가 아닌 결재자
- **WHEN** 견적 담당 사용자를 결재자로 골라 상신하면
- **THEN** 결재자는 승인자만 될 수 있다는 오류가 나고 실행은 담당자 확인 단계로 남는다

### Requirement: 상신 취소
시스템은 결정 전인 승인 대기 실행을 엔지니어가 상신 취소하게 하고, 취소하면 실행을 담당자 확인 단계로 되돌리고 그 상신을 취소됨으로 표시하며 수정 이력에 남겨야 한다(SHALL). 결정이 난 뒤에는 취소할 수 없다(MUST NOT).

#### Scenario: 결정 전 취소
- **WHEN** 엔지니어가 승인 대기인 실행을 상신 취소하면
- **THEN** 실행은 담당자 확인이 되고 후보를 다시 고칠 수 있으며 이력 1건이 남는다

#### Scenario: 승인된 뒤 취소
- **WHEN** 이미 승인된 실행을 상신 취소하려 하면
- **THEN** 승인 대기에서만 취소할 수 있다는 오류가 나고 바뀌지 않는다

### Requirement: 여러 판정 한꺼번에 확정
시스템은 엔지니어가 고른 여러 현재 판정을 한 번에 "제안대로 확정"할 수 있어야 하고(SHALL), 줄마다 확정 이력을 남기며 목록·보증값·제안 포인트는 한 번만 다시 만들어야 한다(SHALL). 고른 판정 중 하나라도 그 실행의 현재 판정이 아니거나 담당자 확인 단계가 아니면 아무것도 바꾸지 않아야 한다(MUST NOT). 판정 값은 바꾸지 않는다.

#### Scenario: 준수 모두 확정
- **WHEN** 담당자 확인 단계에서 아직 확정하지 않은 "준수" 판정 3줄을 한꺼번에 확정하면
- **THEN** 3줄 모두 확정되고 판정 결과는 그대로이며 확정 이력이 3건 남는다

#### Scenario: 현재 판정이 아닌 줄이 섞임
- **WHEN** 고른 판정 중 하나가 비교 제품을 바꾸기 전 판정이면
- **THEN** 오류가 나고 어떤 줄도 확정되지 않으며 이력도 남지 않는다

#### Scenario: 승인 대기 중 한꺼번에 확정
- **WHEN** 승인 대기인 실행의 판정을 한꺼번에 확정하려 하면
- **THEN** 담당자 확인 단계에서만 된다는 오류가 나고 바뀌지 않는다

### Requirement: 문서 추가 뒤 확인 이어받기
시스템은 문서를 더해 다시 분석한 검토에서, 사람이 확정·수정·반려한 판정을 같은 줄(같은 요구값·비교 제품·비교 규칙)의 새 판정에 이어받아야 한다(SHALL). 확정·반려는 상태를, 수정은 고친 판정 값과 사유까지 옮긴다. 확정·반려한 보증값은 새 판정 줄에 다시 이어 그대로 남는다. 위험 조건은 종류·표현·항목·요구사항 묶음이 같으면 확인 상태를 이어받는다. 같은 줄이 없는 판정·위험 조건은 후보로 둔다(CR-08). [제안]

#### Scenario: 확정한 판정은 그대로
- **WHEN** 판정 1줄을 확정한 검토에 추가 문서를 더해 다시 분석하면
- **THEN** 그 줄은 새 판정 번호로 "확정" 그대로이고, 추가 문서에서 새로 나온 판정 줄은 모두 "후보"다

#### Scenario: 수정·반려도 이어받음
- **WHEN** 판정 하나를 질의 후보로 수정하고 다른 하나를 반려한 뒤 문서를 더해 다시 분석하면
- **THEN** 수정한 줄은 "수정"과 질의 후보 그대로, 반려한 줄은 "반려" 그대로다

#### Scenario: 확정한 보증값 그대로
- **WHEN** 값이 있는 보증값 후보를 확정한 뒤 문서를 더해 다시 분석하면
- **THEN** 그 보증값은 확정 그대로이고 지금 판정 줄에 이어져 있다

#### Scenario: 위험 조건 확인도 이어받음
- **WHEN** 포괄 조항 위험 조건 하나를 확정한 뒤 문서를 더해 다시 분석하면
- **THEN** 같은 표현·요구사항의 위험 조건은 확정 그대로이고 확정한 위험 조건은 1개다

### Requirement: 지난 사람 판정 힌트
시스템은 판정마다 요구 원문·표 항목명·요구값 원문(공백·대소문자 무시)과 비교 제품이 같은 판정을 다른 검토에서 사람이 확정·수정했으면, 그중 가장 최근 것의 판정 값, 검토 번호, 사람, 시각, 사유와 지금 판정과 같은지를 함께 내야 한다(SHALL). 반려한 판정은 쓰지 않는다. 힌트는 판정 값과 확인 상태를 바꾸지 않아야 한다(MUST NOT, CR-01·08). 같은 입력이면 같은 힌트다(CR-11). [제안]

#### Scenario: 지난 검토에서 고친 판정
- **WHEN** 앞 검토에서 엔지니어가 준수 판정을 일탈 후보로 고치고, 같은 문서로 새 검토를 돌리면
- **THEN** 새 검토의 같은 줄에 지난 확정 "일탈 후보", 앞 검토 번호, 사유가 있고 지금과 다름으로 표시되며 새 판정 값은 준수 그대로다

#### Scenario: 지난 검토에서 그대로 확정
- **WHEN** 앞 검토에서 엔지니어가 판정을 그대로 확정하고 같은 문서로 새 검토를 돌리면
- **THEN** 새 검토의 같은 줄에 지난 확정이 있고 지금과 같음으로 표시된다

#### Scenario: 사람이 보지 않은 줄
- **WHEN** 앞 검토에서 아무도 확정하지 않았거나 반려한 줄이면
- **THEN** 새 검토의 그 줄에는 지난 확정이 없다

#### Scenario: 제품이 다르면 힌트 없음
- **WHEN** 앞 검토에서 확정한 줄과 요구는 같지만 비교 제품이 다르면
- **THEN** 지난 확정이 없다
